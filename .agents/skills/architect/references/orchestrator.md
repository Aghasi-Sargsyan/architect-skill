# Orchestrator: Fast-Path Commands, Automated Loop, and Monitoring

Reference guide for the `SKILL.md` core. Read it in an interactive session on any fast-path maintenance command (`§0`), before dispatching any task whenever `<skill-folder>/orchestrator/run.mjs` is present (`§1`), and when monitoring loop progress (`§2`). On macOS, the orchestrator is the mandatory default launch path — never bypass it via `invoke_subagent` without reporting the `--dry-run` `✗` and receiving explicit user consent. If you were launched by the orchestrator itself (acceptance inside the loop), this file is not needed.

## 0. Fast-Path Maintenance Commands (`update`, `model`, `compact`, `repair`)

When the user invokes one of these maintenance commands, answer under `[MODE: QUICK FIX · PHASE 2]`, skip reading `PLAN.md`, `decisions.md`, `executor-profiles.md`, and `--status`, and do not re-read `SKILL.md` afterward:

- **Updating the skill (`/architect update` or `/architect:update`):** check `.agent-runs/.lock` and `git status --porcelain` first (in Phase 2 directly): (1) if `.lock` holds a live PID, or `<skill-folder>` / `EXECUTOR.md` has uncommitted tracked changes, stop and warn the user (unless `--force` was requested); (2) if the working tree is clean, run `node <skill-folder>/orchestrator/run.mjs --update`, commit `<skill-folder>` and `EXECUTOR.md` (`arch: update architect skill to <sha>`), and report the version and SHA; (3) if only other project files are dirty, run `--update`, report the version and SHA, and ask before committing `<skill-folder>` and `EXECUTOR.md` (set `ARCHITECT_UPDATE_REF=<tag-or-sha>` when pinning to a specific upstream release).
- **Selecting or changing role models (`/architect model` or `/architect:model`):** run `node <skill-folder>/orchestrator/run.mjs --models` first: (1) **Step 1 (Role choice):** unless the target role was already named (e.g. `/architect model executor`), show current `executor` and `architect` models and ask in `### ❓ Decision Required` which role to configure (`1 — Executor`, `2 — Architect` for headless orchestrator review, noting the interactive chat model is set in the IDE/CLI UI, or `3 — Both`); (2) **Step 2 (Model + effort choice):** list available environment models with effort tiers and ask the user to pick one; (3) **Apply:** run `node <skill-folder>/orchestrator/run.mjs --set-model <executor|architect> <model-id>` (with `--local` if requested or `.local.json` is active) and report the updated files.
- **Migrating to compact layout (`/architect compact` or `/architect:compact`):** check `.agent-runs/.lock` and `git status --porcelain` first: if `.lock` holds a live PID or service files have uncommitted changes, stop and warn the user; otherwise run `node <skill-folder>/orchestrator/run.mjs --compact`, then `--check`, commit (`arch: migrate layout to compact (.architect/)`), and report the migrated paths.
- **Repairing leftover guards after a crash (`/architect repair` or `/architect:repair`):** if an orchestrator process was killed (`SIGKILL`, power loss) leaving `remote.<name>.pushurl = /dev/null/agent-loop-push-disabled`, `.git/hooks/pre-push`, or a stale `.agent-runs/.lock`, run `node <skill-folder>/orchestrator/run.mjs --repair` (refuses while a live PID holds `.lock`; `--check` and the next `installGuards` also auto-recover using `.git/info/agent-loop-guards.json`).

## 1. Readiness Check and Launch

Recommended plan workflow when the orchestrator is present: write `PLAN.md` and `Frozen` tests in the working tree → run `node <skill-folder>/orchestrator/run.mjs --self-check` (deterministic check of Architect commits, monotonicity, and `red-check` of new/modified `referenceTests`) → fix what it reports → create one `arch: plan …` commit → run `node <skill-folder>/orchestrator/run.mjs --dry-run`.

Always run `--self-check` before proposing or launching `npm run agents`, before closing a cycle, and before `git push`. After the `arch: plan …` commit, modifying or deleting `Frozen` test files or orchestrator configs is allowed only in a commit with prefix `arch: fix-frozen <T-NNN|audit>: ` while preserving monotonicity (test/assert counts and config arrays). Historical commit violations (including legitimate test consolidation reducing test/assert counts) can only be waived in the committed `Decisions` of `PLAN.md` via `- WAIVER <sha7>: <rule> — <reason>` (`monotonicity` or `fix-frozen`) by explicit user decision; a WAIVER covers only its rule and its commit — monotonicity is then counted from the waived commit, so a later decrease still fails. Monotonicity is a heuristic over regex match counts: it does not catch an assertion replaced by `assert.ok(true)`, and files created in the cycle are protected only through `Frozen`. The report shows `(<base>..<head>, N commits)`; `EMPTY` means nothing was checked, and a shallow clone fails unless `--base <ref>` is passed. A reference test counts as red only when a test case fails — a whole-file crash, `process.exit`, or a custom `redCheckCommand` without a matching `redCheckConfirmPattern` (`references/stacks.md` §1) is `NOT VERIFIED` and blocks the high-risk task.

After committing the plan, run `node <skill-folder>/orchestrator/run.mjs --dry-run` — a readiness and self-check run without calling a model — and act on the result. Readiness and `--dry-run` never call a model, and `--check` skips the live permission probe (`– permission probe: skipped`) unless `--probe` is passed (`--check --probe` runs the end-to-end permission probe, one paid model call, only when the user asks for it):

- "ready to start" → within a cycle already approved by the user (Phase 2), launch it immediately with `--background` without an extra question (unless the user asked to stop before launching; on first acquaintance or if the cycle is not yet approved — ask: "Start the automated loop for N open tasks? Executor — <model>, review — <model>; the loop consumes model quotas and commits tasks, and never pushes"). Upon launch, reply with a 1-sentence BLUF ("Loop started"), the 4 `- **Label:** value` bullets from `SKILL.md` Step 4 (**Plan commit**, **Checks**, **Tasks**, and **Next step** — stating the background `pid`, `executor`/`architect` models, and chat mode: "only questions, one line per task, and the final summary appear here to save tokens, since every message re-reads the conversation"), and the live-feed command in a standalone `bash` code block (`npm run agents -- --follow`, or `node <skill-folder>/orchestrator/run.mjs --follow` if the project has no such script). Then, in the same turn, start the `--watch --since 0` from the `• next:` line of the `--background` output in the background (Section 2) before ending the turn: a permission question or a stop reaches the chat only through `--watch`, so never end a turn after `--background` without it. A non-zero `--background` exit means the start failed or was not confirmed: report its `✗` lines instead of watching.
- ✗ only in setup (missing config `.architect/config.json` or `.agents/orchestrator.json`, `.agent-runs/` not in `.gitignore`, ✗ in the "allowlist Antigravity" or "allowlist Claude Code" line) → on macOS, initialize automatically without asking whether to use the orchestrator: run `--init` yourself when there is no config (by default it creates `.architect/config.json` with the `compact` layout); populate the config — `runner` (`"agy"` or `"claude"`), `runnerBin` if needed, the user's chosen `executor.model` and `architect.model`; in `blockedScripts` (or `blockedNpmScripts`) list scripts/targets marked "only on explicit user command" (release, sync, writing real data, printing personal data); in `allowedCommands` list verification commands with a subcommand that are not in the base set; set `bypassScanPaths` and `bypassPatterns` according to the project's check-bypass list (JavaScript regular expressions); commit the config and `.gitignore` (`arch: orchestrator setup` or `arch: настройка оркестратора`, explicit paths); run `--check` and `--dry-run` yourself. Ask the user for an explicit `"yes"` **only** before running `--write-permissions` (for `agy` it updates `~/.gemini/antigravity-cli/settings.json`; for `claude` it updates `~/.config/architect/claude/<project>-<hash>.json`; in both cases `--write-permissions` preserves a non-overwriting initial `*.orig.bak` snapshot, writes `*.bak`, and adds missing project rules; for `claude` it also prunes unsafe `allow` rules and archives every pruned rule into `*.pruned.json`, while the shared `agy` file is never pruned — an unsafe rule there stays, keeps `--check` red, and must be removed by the user; a file rule for another project's root is only a note), then re-run `--check` and `--dry-run`. If everything is ✓ — proceed to launching the loop.
- Any other ✗ (dirty working tree, plan error such as unbackticked `Verify` commands, missing CLI for the chosen runner `agy` or `claude`, not logged into the CLI, Windows loop (on Linux the loop runs with an `untested` warning), environment without an adapter) → fix plan/config issues within your scope and re-run `--dry-run`; if an environment blocker remains, report the exact `✗` cause to the user and **never** silently fall back to `invoke_subagent`. Switch to subagent or manual handoff mode only when the orchestrator cannot run on this OS/runner or after explicit user consent.

On the `--write-permissions` question, `"yes"` means only a direct answer from the user; on any other reply, do not change shared agent settings and do not start the loop (ask whether to pause or run in explicit fallback mode).

## 2. Monitoring the Background Loop

This lets the user control the loop from chat, including from a phone. Right after `--background`, the first `--watch` is `--since 0` from its `• next:` line (a new run counts from zero; do not take N from `--status`, which may still show the previous run). When resuming monitoring later, read the current milestone count via `run.mjs --status`, then launch `node <skill-folder>/orchestrator/run.mjs --watch --since N` using the environment's native background execution so the command waits in the background without blocking chat, and end your turn: the environment will wake you when the command finishes. Adapter details: in Claude Code — background command execution; in Antigravity — parameter `WaitMsBeforeAsync: 500`. Do not retell the agents' step-by-step work in chat. The output of `--watch` (except exit code 3) ends with "(milestones: N)" — run every subsequent call as `--watch --since N` with that N so no milestone is missed. By exit code:

- 0 (window elapsed, loop still running) → silently launch `--watch --since N` again;
- 2 (permission question for a command) → the `### 🔐 Command Permission` block from the output is already formatted as "Questions for the user": paste it verbatim at the end of your message after `---`, omitting the "pass the user's answer: …" line (that line is for you). Before the `---` separator, always output 3 plain-language bullets (`- **What the command does:** ...`, `- **Why the agent requested it:** ...` using the `**Why:**` line from the output and the current task goal, and `- **Recommendation:** ...` stating the risk and which option `1`, `2`, or `3` to choose in plain words without raw `command(...)` syntax; for an unfamiliar command explicitly state: "the orchestrator does not recognize this command"). Pass the user's answer via `run.mjs --answer <1|2|3>`, then run `--watch --since N` again. Never answer on the user's behalf and never propose rules broader than those offered in the question;
- 4 (task milestone: "T-012 accepted (9 min); next T-013" or "T-013: rework 1") → output one line in chat verbatim from the output, then run `--watch --since N` again;
- 3 (loop stopped) → distinguish mid-cycle stops from final stops:
  - **3a (mid-cycle stop — open `[ ]` tasks remain, e.g. escalation, `Verify` / `Frozen` mismatch, or interrupted run):** switch to `[MODE: REVIEW / ESCALATION · PHASE 2]`, read `references/auto-review.md`, resolve the blocker or accept the completed task, and reply using the mandatory 5-bullet schema from `references/auto-review.md` §4 (**Verdict**, **Executor & duration**, **Commit**, **Checks**, and **Issues / Next step** — explicitly stating why the loop stopped, any `arch:` / `arch: fix-frozen` commit SHA, and the new `--background` `pid`), then run `--watch --since 0`; never stay in `[MODE: FEATURE · PHASE 2]` or invent custom bullets;
  - **3b (final stop — all tasks `[x]` accepted, or stopped awaiting a user decision):** if no open `[ ]` tasks remain, switch to `[MODE: REVIEW / ESCALATION · PHASE 2]` and close the cycle immediately per `references/retro.md` §1 using its mandatory Cycle Closure chat schema (explicit cycle-complete BLUF + final **Status** bullet at the very bottom stating that the cycle is complete and no open tasks remain); otherwise, start in chat with a 2–4 bullet plain-language explanation of what was accomplished during the run (without file paths, function names, or commit SHAs) and why the loop stopped, then report the technical summary from the output and the `### ❓ Decision Required` block.

When the user asks "how is it going?", run `run.mjs --status` (one short summary; the first line of a running loop ends with `(milestones: N)`, counted exactly as `--watch` counts) — the background `--watch` continues waiting. Milestone lines are English only: `T-012 accepted (9 min); next T-013` and `T-013: rework 1`.

When the user asks to cancel a running loop, run `run.mjs --stop`: it signals only a live lock owner (agent process first, then the guards are restored, then the lock is removed), prints `loop stopped (PID n)` and exits `0`, or prints `no running loop` and exits `1`. A `Verify` timeout (`verifyTimeoutMs`, default 600 s) is an environment stop (`T-NNN: Verify timed out (environment): <command>`) that spends no rework round; a failing `Verify` still goes to rework.

## 3. Subagent, Manual Handoff, and `AGENTS.md` Roles Block

On first run in a new project, offer to add the roles block to `AGENTS.md` (or `CLAUDE.md` / `GEMINI.md`) and commit it together with the first `arch: plan …` commit after approval:
- **Architect session** (explicit `/architect`, or a request to design architecture, draft/update `PLAN.md`, review Executor work, or resolve an escalation — not read-only code Q&A without `/architect`): first read `<skill-folder>/SKILL.md` and follow the Two-Phase Protocol (`[MODE: ... · PHASE 1/2]`).
- **Executor session** (request to execute task `T-NNN` from `PLAN.md`): first read `EXECUTOR.md` and `PLAN.md`, modify only files in `Change` of `T-NNN`, never touch `Frozen` or `PLAN.md`, and run `Check` before committing `T-NNN: ...`.
- **Executor model:** `<Model / Tier>` (chosen by the user; never `inherit` or omitted).

Only when the orchestrator cannot run in the current OS/environment (e.g. Windows, missing `agy`/`claude` binary) or when the user explicitly chose subagent mode instead of the orchestrator, launch the Executor with a standard minimal prompt (`"Read EXECUTOR.md and PLAN.md. Execute task T-NNN and return the report in the format specified in EXECUTOR.md."`) without retelling the task or leaking chat history (when resuming after an escalation, append the Executor's escalation report verbatim and your resolution in one line), and always run `node <skill-folder>/orchestrator/run.mjs --check-task T-NNN` during acceptance whenever `run.mjs` is present (`references/auto-review.md`):

- **Antigravity:** `define_subagent` does not accept a model; `invoke_subagent` accepts `Model` only from `["inherit", "flash_lite", "flash", "pro"]`, without reasoning effort tier or exact model ID. Subagent definitions are stored in the conversation directory (`~/.gemini/antigravity/brain/<id>/`) rather than in the project repository, so `Model` must be passed explicitly on every `invoke_subagent` call (`inherit` is forbidden unless recorded in an ADR).
- **Claude Code:** skills are discovered only in `.claude/skills/`, so link `.claude/skills/architect` to `.agents/skills/architect` (`--init` creates the link inside Claude Code; commit it with the orchestrator setup); `AGENTS.md` is read only when no `CLAUDE.md` exists, otherwise `CLAUDE.md` needs a line `@AGENTS.md` (`--check` warns about both). Set an explicit `model` (alias or full ID) and optional `effort` in `.claude/agents/executor.md` (template: `<skill-folder>/templates/claude-agent-executor.md`) or pass `model` when invoking the subagent; by default Claude Code subagents inherit the parent session model. With the `claude` runner, `<alias>-<effort>` ids (e.g. `opus-high`) run as `--model opus --effort high`. Fast paths use `/architect update` (the `:update` form is unavailable for project skills).
- **Environments without isolated subagents (Gemini CLI, Codex, Cursor, etc.):** run the Executor in a separate chat session.
