# Orchestrator: Running the Automated Loop and Monitoring

Reference guide for the `SKILL.md` core. Read it in an interactive session before dispatching any task whenever the skill folder contains the orchestrator (`<skill-folder>/orchestrator/run.mjs`), and when the user asks about loop progress. On macOS, the orchestrator is the mandatory default launch path — never bypass it via `invoke_subagent` without reporting the `--dry-run` `✗` and receiving explicit user consent. If you were launched by the orchestrator itself (acceptance inside the loop), this file is not needed.

## 1. Readiness Check and Launch

Recommended plan workflow when the orchestrator is present: write `PLAN.md` and `Frozen` tests in the working tree → run `node <skill-folder>/orchestrator/run.mjs --self-check` (deterministic check of Architect commits, monotonicity, and `red-check` of new/modified `referenceTests`) → optionally run `node <skill-folder>/orchestrator/run.mjs --audit-plan` (paid live read-only cross-model plan audit per `references/plan-audit.md`, only after explicit user confirmation; at most 1 re-run per cycle base; resolve every `blocker`/`important` in `PLAN.md` as `- A-N [blocker|important]: принято` / `accepted` or `… отклонено: <reason>` / `rejected: <reason>`) → apply fixes → create one `arch: plan …` commit → run `node <skill-folder>/orchestrator/run.mjs --dry-run`.

Always run `--self-check` before proposing or launching `npm run agents`, before closing a cycle, and before `git push`. After the `arch: plan …` commit, modifying or deleting `Frozen` test files or orchestrator configs is allowed only in a commit with prefix `arch: fix-frozen <T-NNN|audit>: ` while preserving monotonicity (test/assert counts and config arrays). Historical commit violations without `fix-frozen` can only be waived in `Decisions` of `PLAN.md` via `- WAIVER <sha7>: <rule> — <reason>` by explicit user decision.

After committing the plan, run `node <skill-folder>/orchestrator/run.mjs --dry-run` — a readiness and self-check run without calling a model — and act on the result:

- "ready to start" → within a cycle already approved by the user (Phase 2), launch it immediately with `--background` without an extra question (unless the user asked to stop before launching; on first acquaintance or if the cycle is not yet approved — ask: "Start the automated loop for N open tasks? Executor — <model>, review — <model>; the loop consumes model quotas and commits tasks, and never pushes"). Upon launch, reply with a 1-sentence BLUF ("Loop started"), the 4 `- **Label:** value` bullets from `SKILL.md` Step 4 (**Plan commit**, **Checks**, **Tasks**, and **Next step** — stating the background `pid`, `executor`/`architect` models, and chat mode: "only questions, one line per task, and the final summary appear here to save tokens, since every message re-reads the conversation"), and the live-feed command in a standalone `bash` code block (`npm run agents -- --follow`, or `node <skill-folder>/orchestrator/run.mjs --follow` if the project has no such script). Then immediately proceed to monitoring (Section 2).
- ✗ only in setup (missing config `.architect/config.json` or `.agents/orchestrator.json`, `.agent-runs/` not in `.gitignore`, ✗ in the "allowlist Antigravity" or "allowlist Claude Code" line) → on macOS, initialize automatically without asking whether to use the orchestrator: run `--init` yourself when there is no config (by default it creates `.architect/config.json` with the `compact` layout); populate the config — `runner` (`"agy"` or `"claude"`), `runnerBin` if needed, the user's chosen `executor.model` and `architect.model`; in `blockedScripts` (or `blockedNpmScripts`) list scripts/targets marked "only on explicit user command" (release, sync, writing real data, printing personal data); in `allowedCommands` list verification commands with a subcommand that are not in the base set; set `bypassScanPaths` and `bypassPatterns` according to the project's check-bypass list (JavaScript regular expressions); commit the config and `.gitignore` (`arch: orchestrator setup` or `arch: настройка оркестратора`, explicit paths); run `--check` and `--dry-run` yourself. Ask the user for an explicit `"yes"` **only** before running `--write-permissions` (for `agy` it updates `~/.gemini/antigravity-cli/settings.json`; for `claude` it updates `~/.config/architect/claude/<project>-<hash>.json`; in both cases `--write-permissions` backs up `*.bak`, adds missing project rules, and prunes unsafe or cross-project `allow` rules), then re-run `--check` and `--dry-run`. If everything is ✓ — proceed to launching the loop.
- Any other ✗ (dirty working tree, plan error, missing CLI for the chosen runner `agy` or `claude`, not logged into the CLI, Linux/Windows loop, environment without an adapter) → fix plan/config issues within your scope and re-run `--dry-run`; if an environment blocker remains, report the exact `✗` cause to the user and **never** silently fall back to `invoke_subagent`. Switch to subagent or manual handoff mode only when the orchestrator cannot run on this OS/runner or after explicit user consent.

On the `--write-permissions` question, `"yes"` means only a direct answer from the user; on any other reply, do not change shared agent settings and do not start the loop (ask whether to pause or run in explicit fallback mode).

## 2. Monitoring the Background Loop

This lets the user control the loop from chat, including from a phone. Before the first long `--watch` (or when resuming monitoring), read the current milestone count via `run.mjs --status`, then launch `node <skill-folder>/orchestrator/run.mjs --watch --since N` using the environment's native background execution so the command waits in the background without blocking chat, and end your turn: the environment will wake you when the command finishes. Adapter details: in Claude Code — background command execution; in Antigravity — parameter `WaitMsBeforeAsync: 500`. Do not retell the agents' step-by-step work in chat. The output of `--watch` (except exit code 3) ends with "(milestones: N)" — run every subsequent call as `--watch --since N` with that N so no milestone is missed. By exit code:

- 0 (window elapsed, loop still running) → silently launch `--watch --since N` again;
- 2 (permission question for a command) → the `### 🔐 Command Permission` block from the output is already formatted as "Questions for the user": paste it verbatim at the end of your message after `---`, omitting the "pass the user's answer: …" line (that line is for you). Before the `---` separator, always output 3 plain-language bullets (`- **What the command does:** ...`, `- **Why the agent requested it:** ...` using the `**Why:**` line from the output and the current task goal, and `- **Recommendation:** ...` stating the risk and which option `1`, `2`, or `3` to choose in plain words without raw `command(...)` syntax; for an unfamiliar command explicitly state: "the orchestrator does not recognize this command"). Pass the user's answer via `run.mjs --answer <1|2|3>`, then run `--watch --since N` again. Never answer on the user's behalf and never propose rules broader than those offered in the question;
- 4 (task milestone: "T-012 accepted (9 min); next T-013" or "T-013: rework 1") → output one line in chat verbatim from the output, then run `--watch --since N` again;
- 3 (loop stopped) → distinguish mid-cycle stops from final stops:
  - **3a (mid-cycle stop — open `[ ]` tasks remain, e.g. escalation, `Verify` / `Frozen` mismatch, or interrupted run):** switch to `[MODE: REVIEW / ESCALATION · PHASE 2]`, read `references/auto-review.md`, resolve the blocker or accept the completed task, and reply using the mandatory 5-bullet schema from `references/auto-review.md` §4 (**Verdict**, **Executor & duration**, **Commit**, **Checks**, and **Issues / Next step** — explicitly stating why the loop stopped, any `arch:` / `arch: fix-frozen` commit SHA, and the new `--background` `pid`), then run `--watch --since 0`; never stay in `[MODE: FEATURE · PHASE 2]` or invent custom bullets;
  - **3b (final stop — all tasks `[x]` accepted, or stopped awaiting a user decision):** if no open `[ ]` tasks remain, switch to `[MODE: REVIEW / ESCALATION · PHASE 2]` and close the cycle immediately per `references/retro.md` §1; otherwise, start in chat with a 2–4 bullet plain-language explanation of what was accomplished during the run (without file paths, function names, or commit SHAs) and why the loop stopped, then report the technical summary from the output and the `### ❓ Decision Required` block.

When the user asks "how is it going?", run `run.mjs --status` (one short summary) — the background `--watch` continues waiting.

## 3. Subagent, Manual Handoff, and `AGENTS.md` Roles Block

On first run in a new project, offer to add the roles block to `AGENTS.md` (or `CLAUDE.md` / `GEMINI.md`) and commit it together with the first `arch: plan …` commit after approval:
- **Architect session** (`/architect` or architecture, `PLAN.md`, review, or diagnosis request): first read `<skill-folder>/SKILL.md` and follow the Two-Phase Protocol (`[MODE: ... · PHASE 1/2]`).
- **Executor session** (request to execute task `T-NNN` from `PLAN.md`): first read `EXECUTOR.md` and `PLAN.md`, modify only files in `Change` of `T-NNN`, never touch `Frozen` or `PLAN.md`, and run `Check` before committing `T-NNN: ...`.
- **Executor model:** `<Model / Tier>` (chosen by the user; never `inherit` or omitted).

Only when the orchestrator cannot run in the current OS/environment (e.g. Linux/Windows loop, missing `agy`/`claude` binary) or when the user explicitly chose subagent mode instead of the orchestrator, launch the Executor with a standard minimal prompt (`"Read EXECUTOR.md and PLAN.md. Execute task T-NNN and return the report in the format specified in EXECUTOR.md."`) without retelling the task or leaking chat history, and always run `node <skill-folder>/orchestrator/run.mjs --check-task T-NNN` during acceptance whenever `run.mjs` is present (`references/auto-review.md`):

- **Antigravity:** `define_subagent` does not accept a model; `invoke_subagent` accepts `Model` only from `["inherit", "flash_lite", "flash", "pro"]`, without reasoning effort tier or exact model ID. Subagent definitions are stored in the conversation directory (`~/.gemini/antigravity/brain/<id>/`) rather than in the project repository, so `Model` must be passed explicitly on every `invoke_subagent` call (`inherit` is forbidden unless recorded in an ADR).
- **Claude Code:** set an explicit `model` field in `.claude/agents/executor.md` (template: `<skill-folder>/templates/claude-agent-executor.md`) or pass `model` when invoking the subagent; by default Claude Code subagents inherit the parent session model.
- **Environments without isolated subagents (Gemini CLI, Codex, Cursor, etc.):** run the Executor in a separate chat session.
