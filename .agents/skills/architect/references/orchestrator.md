# Orchestrator: Running the Automated Loop and Monitoring

Reference guide for the `SKILL.md` core. Read it in an interactive session after committing a plan or new tasks if the skill folder contains the orchestrator (`<skill-folder>/orchestrator/run.mjs`), and when the user asks about loop progress. If you were launched by the orchestrator itself (acceptance inside the loop), this file is not needed.

## 1. Readiness Check and Launch

Before committing `arch: plan …`, run `node <skill-folder>/orchestrator/run.mjs --self-check` (deterministic check of Architect commits, monotonicity, `eval` evidence, and `red-check` of new/modified `referenceTests`); optionally run `node <skill-folder>/orchestrator/run.mjs --audit-plan` (paid live read-only cross-model plan audit per `references/plan-audit.md`, only after explicit user confirmation; at most 1 re-run per cycle base).

After committing the plan, run `node <skill-folder>/orchestrator/run.mjs --dry-run` — a readiness and self-check run without calling a model — and act on the result:

- "ready to start" → within a cycle already approved by the user (Phase 2), launch it immediately with `--background` without an extra question (unless the user asked to stop before launching; on first acquaintance or if the cycle is not yet approved — ask: "Start the automated loop for N open tasks? Executor — <model>, review — <model>; the loop consumes model quotas and commits tasks, and never pushes"). Upon launch, reply briefly in two lines: "Loop started. Detailed live feed in your computer terminal: `npm run agents -- --follow`" (if the project has no such script — `node <skill-folder>/orchestrator/run.mjs --follow`) and "I do not stream it in chat to save tokens: every message re-reads the entire conversation, so only questions, one line per task, and the final summary will appear here". Then immediately proceed to monitoring (Section 2).
- ✗ only in setup (missing config `.architect/config.json` or `.agents/orchestrator.json`, `.agent-runs/` not in `.gitignore`, ✗ in the "Antigravity allowlist" or "Claude Code allowlist" line) → ask: "Automated mode is not configured in this project. Configure it?" and list what will be done. Upon an explicit "yes": run `--init` if there is no config (by default it creates `.architect/config.json` with the `compact` layout); populate the config — `runner` (`"agy"` or `"claude"`), `runnerBin` if needed, models `executor.model` and `architect.model`; in `blockedScripts` (or `blockedNpmScripts`) list scripts/targets marked "only on explicit user command" (release, sync, writing real data, printing personal data); in `allowedCommands` list verification commands with a subcommand that are not in the base set; set `bypassScanPaths` and `bypassPatterns` according to the project's check-bypass list (JavaScript regular expressions); commit the config and `.gitignore` (`arch: настройка оркестратора`, explicit paths); then run `--write-permissions` (for `agy` it updates `~/.gemini/antigravity-cli/settings.json`; for `claude` it creates the project file `~/.config/architect/claude/<project>-<hash>.json` with rules and OS sandbox) and `--check` (one short model probe). If everything is ✓ — proceed to launching the loop without re-checking.
- Any other ✗ (dirty working tree, plan error, missing CLI for the chosen runner `agy` or `claude`, not logged into the CLI, Windows, environment without an adapter) → state the cause and fix what is within your scope; if the orchestrator does not work in this environment — give the user the Executor handoff prompt as in manual mode.

On the setup question (`--write-permissions`), "yes" means only a direct answer from the user; on any other reply, do not change settings and do not start the loop.

## 2. Monitoring the Background Loop

This lets the user control the loop from chat, including from a phone. Before the first long `--watch` (or when resuming monitoring), read the current milestone count via `run.mjs --status`, then launch `node <skill-folder>/orchestrator/run.mjs --watch --since N` using the environment's native background execution so the command waits in the background without blocking chat, and end your turn: the environment will wake you when the command finishes. Adapter details: in Claude Code — background command execution; in Antigravity — parameter `WaitMsBeforeAsync: 500`. Do not retell the agents' step-by-step work in chat. The output of `--watch` (except exit code 3) ends with "(milestones: N)" — run every subsequent call as `--watch --since N` with that N so no milestone is missed. By exit code:

- 0 (window elapsed, loop still running) → silently launch `--watch --since N` again;
- 2 (permission question for a command) → the `### 🔐 Command Permission` block from the output is already formatted as "Questions for the user": paste it verbatim at the end of your message after `---`, omitting the "pass the user's answer: …" line (that line is for you). Pass the user's answer via `run.mjs --answer <1|2|3>`, then run `--watch --since N` again. Never answer on the user's behalf and never propose rules broader than those offered in the question;
- 4 (task milestone: "T-012 accepted (9 min); next T-013" or "T-013: rework 1") → output one line in chat verbatim from the output, then run `--watch --since N` again;
- 3 (loop stopped) → report the summary from the output and what comes next.

When the user asks "how is it going?", run `run.mjs --status` (one short summary) — the background `--watch` continues waiting.
