# Orchestrator: Running the Automated Loop and Monitoring

Reference guide for the `SKILL.md` core. Read it in an interactive session after committing a plan or new tasks if the skill folder contains the orchestrator (`<skill-folder>/orchestrator/run.mjs`), and when the user asks about loop progress. If you were launched by the orchestrator itself (acceptance inside the loop), this file is not needed.

## 1. Readiness Check and Launch

Recommended plan workflow when the orchestrator is present: write `PLAN.md` and `Frozen` tests in the working tree → run `node <skill-folder>/orchestrator/run.mjs --self-check` (deterministic check of Architect commits, monotonicity, and `red-check` of new/modified `referenceTests`) → optionally run `node <skill-folder>/orchestrator/run.mjs --audit-plan` (paid live read-only cross-model plan audit per `references/plan-audit.md`, only after explicit user confirmation; at most 1 re-run per cycle base; resolve every `blocker`/`important` in `PLAN.md` as `- A-N [blocker|important]: принято` / `accepted` or `… отклонено: <reason>` / `rejected: <reason>`) → apply fixes → create one `arch: plan …` commit → run `node <skill-folder>/orchestrator/run.mjs --dry-run`.

Always run `--self-check` before proposing or launching `npm run agents`, before closing a cycle, and before `git push`. After the `arch: plan …` commit, modifying or deleting `Frozen` test files or orchestrator configs is allowed only in a commit with prefix `arch: fix-frozen <T-NNN|audit>: ` while preserving monotonicity (test/assert counts and config arrays). Historical commit violations without `fix-frozen` can only be waived in `Decisions` of `PLAN.md` via `- WAIVER <sha7>: <rule> — <reason>` by explicit user decision.

After committing the plan, run `node <skill-folder>/orchestrator/run.mjs --dry-run` — a readiness and self-check run without calling a model — and act on the result:

- "ready to start" → within a cycle already approved by the user (Phase 2), launch it immediately with `--background` without an extra question (unless the user asked to stop before launching; on first acquaintance or if the cycle is not yet approved — ask: "Start the automated loop for N open tasks? Executor — <model>, review — <model>; the loop consumes model quotas and commits tasks, and never pushes"). Upon launch, reply with a 1-sentence BLUF ("Loop started"), `- **Label:** value` bullets (one per line: plan commit, checks, and chat mode — "only questions, one line per task, and the final summary appear here to save tokens, since every message re-reads the conversation"), and the live-feed command in a standalone `bash` code block (`npm run agents -- --follow`, or `node <skill-folder>/orchestrator/run.mjs --follow` if the project has no such script). Then immediately proceed to monitoring (Section 2).
- ✗ only in setup (missing config `.architect/config.json` or `.agents/orchestrator.json`, `.agent-runs/` not in `.gitignore`, ✗ in the "Antigravity allowlist" or "Claude Code allowlist" line) → if the user wants the automated orchestrator, run `--init` yourself when there is no config (by default it creates `.architect/config.json` with the `compact` layout); populate the config — `runner` (`"agy"` or `"claude"`), `runnerBin` if needed, the user's chosen `executor.model` and `architect.model`; in `blockedScripts` (or `blockedNpmScripts`) list scripts/targets marked "only on explicit user command" (release, sync, writing real data, printing personal data); in `allowedCommands` list verification commands with a subcommand that are not in the base set; set `bypassScanPaths` and `bypassPatterns` according to the project's check-bypass list (JavaScript regular expressions); commit the config and `.gitignore` (`arch: orchestrator setup` or `arch: настройка оркестратора`, explicit paths); run `--check` and `--dry-run` yourself. Ask the user for an explicit `"yes"` **only** before running `--write-permissions` (for `agy` it updates `~/.gemini/antigravity-cli/settings.json`; for `claude` it creates `~/.config/architect/claude/<project>-<hash>.json` with rules and OS sandbox), then re-run `--check` and `--dry-run`. If everything is ✓ — proceed to launching the loop.
- Any other ✗ (dirty working tree, plan error, missing CLI for the chosen runner `agy` or `claude`, not logged into the CLI, Windows, environment without an adapter) → state the cause and fix what is within your scope; if the orchestrator does not work in this environment — give the user the Executor handoff prompt as in manual mode.

On the `--write-permissions` question, `"yes"` means only a direct answer from the user; on any other reply, do not change shared agent settings and do not start the loop.

## 2. Monitoring the Background Loop

This lets the user control the loop from chat, including from a phone. Before the first long `--watch` (or when resuming monitoring), read the current milestone count via `run.mjs --status`, then launch `node <skill-folder>/orchestrator/run.mjs --watch --since N` using the environment's native background execution so the command waits in the background without blocking chat, and end your turn: the environment will wake you when the command finishes. Adapter details: in Claude Code — background command execution; in Antigravity — parameter `WaitMsBeforeAsync: 500`. Do not retell the agents' step-by-step work in chat. The output of `--watch` (except exit code 3) ends with "(milestones: N)" — run every subsequent call as `--watch --since N` with that N so no milestone is missed. By exit code:

- 0 (window elapsed, loop still running) → silently launch `--watch --since N` again;
- 2 (permission question for a command) → the `### 🔐 Command Permission` block from the output is already formatted as "Questions for the user": paste it verbatim at the end of your message after `---`, omitting the "pass the user's answer: …" line (that line is for you). Before the `---` separator, accompany `### 🔐 Command Permission` with one plain-language line (what the command does, its risk, and the recommended answer), and for an unfamiliar command explicitly state: "the orchestrator does not recognize this command". Pass the user's answer via `run.mjs --answer <1|2|3>`, then run `--watch --since N` again. Never answer on the user's behalf and never propose rules broader than those offered in the question;
- 4 (task milestone: "T-012 accepted (9 min); next T-013" or "T-013: rework 1") → output one line in chat verbatim from the output, then run `--watch --since N` again;
- 3 (loop stopped) → report the summary from the output and what comes next.

When the user asks "how is it going?", run `run.mjs --status` (one short summary) — the background `--watch` continues waiting.

## 3. Subagent, Manual Handoff, and `AGENTS.md` Roles Block

On first run in a new project, offer to add the roles block to `AGENTS.md` (or `CLAUDE.md` / `GEMINI.md`) and commit it together with the first `arch: plan …` commit after approval:
- **Architect session** (`/architect` or architecture, `PLAN.md`, review, or diagnosis request): first read `<skill-folder>/SKILL.md` and follow the Two-Phase Protocol (`[MODE: ... · PHASE 1/2]`).
- **Executor session** (request to execute task `T-NNN` from `PLAN.md`): first read `EXECUTOR.md` and `PLAN.md`, modify only files in `Change` of `T-NNN`, never touch `Frozen` or `PLAN.md`, and run `Check` before committing `T-NNN: ...`.
- **Executor model:** `<Model / Tier>` (chosen by the user; never `inherit` or omitted).

When the orchestrator is not configured or cannot run in the current environment, launch the Executor with a standard minimal prompt (`"Read EXECUTOR.md and PLAN.md. Execute task T-NNN and return the report in the format specified in EXECUTOR.md."`) without retelling the task or leaking chat history:

- **Antigravity:** `define_subagent` does not accept a model; `invoke_subagent` accepts `Model` only from `["inherit", "flash_lite", "flash", "pro"]`, without reasoning effort tier or exact model ID. Subagent definitions are stored in the conversation directory (`~/.gemini/antigravity/brain/<id>/`) rather than in the project repository, so `Model` must be passed explicitly on every `invoke_subagent` call (`inherit` is forbidden unless recorded in an ADR).
- **Claude Code:** set an explicit `model` field in `.claude/agents/executor.md` (template: `<skill-folder>/templates/claude-agent-executor.md`) or pass `model` when invoking the subagent; by default Claude Code subagents inherit the parent session model.
- **Environments without isolated subagents (Gemini CLI, Codex, Cursor, etc.):** run the Executor in a separate chat session.
